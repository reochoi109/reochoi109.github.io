프로젝트 개요

DTN(Digital Twin Network)은 실제 교통 데이터를 기반으로 도로의 교통 흐름을 디지털 공간에 재현하고, 운영 대안을 가상으로 실험하는 교통 디지털트윈 시스템입니다.

저는 사용자 클라이언트와 교통 시뮬레이션 서버 사이를 연결하는 중계 서버를 구축했습니다. 중계 서버는 분석 요청을 시뮬레이션 작업으로 전달하고, 실행 상태와 결과를 수집·가공·저장한 뒤 API와 WebSocket으로 클라이언트에 제공합니다.

프로젝트 목적

DTN의 목적은 신호 운영 변경이나 사고·공사 같은 시나리오를 실제 도로에 적용하기 전에 검증하고, 교통량·통행속도·대기행렬·서비스 수준(LOS)·탄소배출량 등의 변화를 비교해 교통정책의 판단 근거를 제공하는 것입니다.

서버 관점에서는 즉시 응답하기 어려운 장시간 작업을 비동기로 분리하고, 서로 성격이 다른 정적 분석 지표와 동적 트윈 데이터를 하나의 작업 상태로 연결해 조회와 재생이 가능한 서비스 데이터로 만드는 것이 핵심 목표였습니다.

담당 역할

별도의 백엔드 개발자 없이 서버 영역 전체를 담당했습니다. 요구사항 분석과 API 계약부터 Kafka 기반 비동기 처리, PostgreSQL과 파일 저장 구조, WebSocket 전달, Docker 실행 환경, Swagger/OpenAPI 문서까지 직접 설계·구현했습니다.

교통 시뮬레이션 모델과 사용자 화면은 담당 범위가 아니었으며, 두 시스템을 연결해 시뮬레이션 결과를 서비스 데이터로 제공하는 백엔드에 집중했습니다.

주요 구현

분석 작업 생명주기

  • 분석 요청, 진행 상태, 완료 결과를 다루는 REST API와 공통 응답 형식 구현
  • 요청마다 UUID를 발급하고 분석 일련번호와 연결해 비동기 작업의 요청·진행·성공·실패 상태를 추적
  • 완료되지 않은 작업은 제한 시간 이후 만료 처리하고, 서버 재시작 시 남아 있는 진행 상태를 정리해 실제 실행 상태와 데이터베이스 상태의 불일치 방지
  • Swagger/OpenAPI로 클라이언트와 서버 간 API 계약 문서화

정적·동적 결과 분리 처리

  • Kafka로 분석 조건을 전달하고 UUID를 기준으로 시뮬레이션 결과를 비동기로 수신
  • 교통량, LOS·제어지체, 탄소배출량, 신호 주기, 구간 속도·점유율 등의 정적 지표는 유형별로 분리해 PostgreSQL에 일괄 저장
  • 차량 객체, 신호 상태, 차로 대기행렬, 구간 속도, 과포화 정보 등의 동적 데이터는 시점과 패킷 순서를 유지하며 별도 처리
  • 정적 지표 저장이 모두 끝난 시점을 동적 처리 흐름에 알리고, 두 결과가 준비된 뒤에만 작업 완료와 결과 파일 상태를 갱신

트윈 데이터 가공

  • 시뮬레이터의 차로 번호를 서비스 데이터베이스의 차로 ID로 매핑해 클라이언트가 사용할 식별 체계로 변환
  • 과포화 값을 원활·지연·정체 상태로 분류하고, 상태가 달라질 때 해당 표시 위치를 동적 데이터에 결합
  • 교통량을 전체·차종·이동류 단위로 조회할 수 있도록 집계 응답을 구성하고 지표별 REST API로 제공

결과 재생과 다중 사용자 전달

  • 완료된 9,000개 시점 데이터를 시간순 JSON Lines 파일로 구성하고 tar.gz 형식으로 압축 보관
  • 재생 요청마다 사용 가능한 WebSocket 포트를 할당하고, 압축 파일을 세션별 임시 경로에 해제해 서로 다른 결과가 충돌하지 않도록 분리
  • 파일을 한 줄씩 읽어 WebSocket으로 순차 전송하고 마지막 패킷을 명시해 클라이언트가 재생 종료 시점을 판단하도록 구현
  • 재생 완료·타임아웃 시 서버와 임시 파일을 정리하고 포트를 풀에 반환해 다음 요청에서 재사용

문제 해결 및 개선

9,000개 시점 데이터의 메모리 점유

15분 분량의 동적 결과는 900개 청크, 총 9,000개 시점 데이터로 들어옵니다. 초기 파일 생성 방식은 수신된 청크를 다시 하나의 큰 맵으로 합친 뒤 전체를 한 번에 JSON 직렬화했기 때문에, 이미 보관 중인 결과 외에 통합 맵과 직렬화 버퍼가 추가로 필요했습니다.

파일 생성 방식을 시점별 순차 기록으로 변경했습니다. 청크와 시점 번호를 순회하면서 한 시점만 작은 맵으로 구성해 JSON Lines 한 줄로 기록함으로써, 9,000개 시점을 하나의 결과 객체와 바이트 배열로 다시 만드는 과정을 제거했습니다.

이 구조로 파일 생성 단계의 순간적인 추가 메모리 점유를 제한하고, 시점 순서를 보장하는 스트리밍 친화적인 결과 파일을 만들었습니다. 기록이 끝난 파일은 tar.gz로 압축하고 원본을 정리해 보관과 재생 단위를 일치시켰습니다.

비동기 결과의 완료 조건 동기화

정적 지표와 동적 트윈 데이터는 서로 다른 Kafka 흐름으로 도착하므로 한쪽 수신만 끝난 시점에 작업을 완료 처리하면 조회 결과나 재생 파일이 불완전할 수 있었습니다.

정적 결과의 필수 데이터 유형이 모두 저장되면 내부 채널로 UUID와 분석 일련번호를 동적 처리기에 전달하고, 동적 패킷 수신 완료 여부와 결합해 파일 생성과 상태 변경을 시작하도록 구성했습니다. 실패 메시지와 제한 시간 초과도 같은 작업 상태에 반영해 장시간 작업이 진행 중으로 남지 않도록 했습니다.

결과

  • 장시간 시뮬레이션을 API 요청과 분리해 작업 단위로 추적할 수 있는 비동기 처리 흐름 구축
  • 정적 지표 저장과 동적 트윈 파일 생성을 동기화해 완료 상태의 일관성 확보
  • 9,000개 시점 결과의 통합 객체 생성을 없애고 JSON Lines 기반 순차 파일 생성 구조 적용
  • 압축 보관, 세션별 압축 해제, WebSocket 포트 회수까지 이어지는 결과 재생 수명주기 구축
  • 분석 요청, 상태 확인, 지표 조회, 결과 재생을 하나의 백엔드 인터페이스로 제공
