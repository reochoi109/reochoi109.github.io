PROJECT 01 · 2024.09 — 2024.12

TMS-DTN 디지털트윈 중계 서버

담당중계 서버 전체 설계·개발

  • Go
  • Kafka
  • PostgreSQL
  • WebSocket

01문제

처음에는 시뮬레이션 결과를 PostgreSQL의 JSONB로 관리하는 방식을 검토했습니다. 하지만 15분 분량의 차량 위치와 신호 상태를 실제로 다뤄보니 데이터가 커질수록 조회가 느려지고, 전체 결과를 메모리에 올려 전송하면 메모리 사용량도 함께 커졌습니다. 정적 분석 지표와 시간순 재생 데이터가 같은 저장 방식에 맞지 않는다는 점이 문제였습니다.

02해결방법

  1. 시뮬레이션 서버와 프론트엔드 개발자와 통신 방식과 데이터 규격을 맞추고, 요청마다 작업 ID를 발급해 Kafka로 분석 요청과 결과를 비동기 처리했습니다.
  2. 분석 후 값이 바뀌지 않는 지표는 PostgreSQL에 저장하고, 순서대로 재생해야 하는 차량 위치와 신호 상태는 JSON Lines 파일로 분리했습니다.
  3. 사용자가 재생을 요청하면 전체 파일을 메모리에 올리지 않고 한 줄씩 읽어 WebSocket으로 바로 전송하도록 바꿨습니다.

03결과

정적 결과는 API로 조회하고 동적 결과는 WebSocket으로 순차 재생하는 흐름을 완성했습니다. 전체 파일 로딩을 기다리지 않고 재생을 시작할 수 있었고, 파일 생성과 재생 과정에서 추가 메모리 점유도 제한했습니다. 개발한 시스템은 지자체에 납품되어 신호체계 변경 효과를 사전에 확인하는 데 사용됐습니다.

이 프로젝트에서 배운 것

처음 정한 저장 방식을 끝까지 유지하는 것보다, 데이터가 실제로 어떻게 조회되고 재생되는지를 확인한 뒤 구조를 바꾸는 것이 중요하다는 것을 배웠습니다. 이후에는 기술을 먼저 고르기보다 데이터의 성격과 사용 방식을 먼저 봅니다.

PROJECT 02 · 2023.07 — 2023.09

Headway·GAP 교통 지표 분석

담당분류·계산·유효성 검사·집계 및 DB 연계

  • Go
  • MySQL
  • Tibero
  • ODBC

01문제

처음에는 차량 통과 시각의 차이를 계산하는 비교적 단순한 기능이라고 생각했습니다. 테스트 데이터에서는 정상적으로 보였지만 실제 지자체 데이터를 연결하자 예상 범위를 벗어나는 값이 반복됐습니다. 계산식보다 카메라 화각, 설치 위치, 대형차 뒤의 차량 가림과 같은 실제 환경이 결과를 더 크게 흔들고 있었습니다.

02해결방법

  1. 이상값을 단순 삭제하지 않고 실제 영상과 검지 기록을 나란히 보며 어떤 상황에서 오차가 생기는지 추적했습니다.
  2. 차로별 데이터를 시간순으로 정렬하고 같은 신호 구간의 연속 차량만 비교했습니다. GAP에는 앞 차량의 차종별 전장과 속도로 계산한 점유 시간을 반영했습니다.
  3. 영상 대조 결과를 기준으로 보정값을 조정하고 Headway 0.8초 이하·3.5초 이상, GAP 0.01초 미만을 제외했습니다. 신호 시작 직후 초기 6대도 전체 흐름을 대표하기 어렵다고 판단해 별도로 집계했습니다.

03결과

보정과 유효성 검사를 통과한 차량 쌍을 차로·신호 주기별 지표로 만들고 공동 Tibero 데이터베이스에 적재했습니다. 이 결과는 교통 흐름과 교차로 연계 상태를 확인하는 분석 자료로 제공됐습니다.

이 프로젝트에서 배운 것

코드가 계산식을 정확히 구현했다고 해서 결과까지 정확한 것은 아니었습니다. 실제 영상과 데이터를 함께 확인하면서, 현실의 예외를 설명할 수 있는 기준을 만들고 계속 보완하는 일이 분석 로직의 핵심이라는 것을 배웠습니다.

PROJECT 03 · 2025.01 — 2025.07

Goutils 사내 공용 Go 모듈

담당공용 패키지 개발·버전 배포·사용 문서화

  • Go Modules
  • Kafka
  • WebSocket
  • RTSP

01문제

서비스를 옮겨 다니며 개발할 때마다 DB 연결, 로깅, Kafka와 WebSocket 같은 기반 코드를 다시 확인해야 했습니다. 비슷한 코드가 여러 저장소에 있었지만 구현과 버전이 조금씩 달라, 한 곳을 고쳐도 다른 서비스에는 그대로 반영할 수 없었습니다.

02해결방법

  1. 실제 서비스에서 반복해서 사용하던 코드를 기준으로 DB pool, 로깅, 검증, HTTP, Kafka, WebSocket, TCP와 RTSP 기능을 책임별 패키지로 나눴습니다.
  2. 공용 모듈만 보고 동작을 가정하지 않고, 기능 브랜치를 사용하는 대상 서비스에서 먼저 검증했습니다.
  3. 검증이 끝난 변경은 Git tag로 버전을 만들고 각 서비스의 go.mod에 명시했습니다. 다른 개발자가 적용할 수 있도록 사용법과 릴리스 내역도 함께 기록했습니다.

03결과

서비스마다 복사해 두었던 기반 기능을 버전이 있는 Go 모듈로 사용할 수 있게 했습니다. 어떤 서비스가 어느 버전을 사용하는지 명확해졌고, 변경을 실제 서비스에서 검증한 뒤 배포하는 흐름을 만들었습니다.

이 프로젝트에서 배운 것

공용화는 코드를 한 저장소로 옮기는 것만으로 끝나지 않았습니다. 사용하는 서비스에서 검증할 방법, 적용 버전, 다른 개발자가 따라 할 문서까지 있어야 실제 공용 모듈로 기능한다는 것을 배웠습니다.
