## 1. OSI 7계층과 TCP/IP 모델

### 면접 답변

> OSI 7계층은 네트워크 통신 과정을 역할에 따라 7단계로 나눈 참조 모델입니다. 계층마다 책임을 분리하기 때문에 특정 계층의 구현이 바뀌어도 다른 계층에 미치는 영향을 줄이고, 장애가 발생한 위치도 계층별로 추적할 수 있습니다.
>
> 실제 인터넷은 OSI 모델을 그대로 구현하기보다 이를 단순화한 TCP/IP 모델을 중심으로 동작합니다. TCP/IP 4계층은 응용, 전송, 인터넷, 네트워크 접근 계층으로 구분합니다.

![OSI 7계층과 TCP/IP 모델 비교](./static/images/study/network-layer-models.svg)

### 계층 비교

| OSI 7계층 | TCP/IP 4계층 | 주요 역할 | 대표 프로토콜·기술 |
|---|---|---|---|
| 7. 응용 계층 | 응용 계층 | 사용자에게 네트워크 서비스 제공 | HTTP, DNS, SMTP, SSH |
| 6. 표현 계층 | 응용 계층 | 인코딩, 압축, 암호화, 데이터 형식 변환 | TLS, JSON, UTF-8 |
| 5. 세션 계층 | 응용 계층 | 통신 세션의 생성·유지·종료 | RPC, 세션 관리 |
| 4. 전송 계층 | 전송 계층 | 프로세스 간 통신, 신뢰성, 흐름 제어 | TCP, UDP |
| 3. 네트워크 계층 | 인터넷 계층 | IP 주소 기반 라우팅 | IPv4, IPv6, ICMP |
| 2. 데이터 링크 계층 | 네트워크 접근 계층 | 같은 네트워크의 노드 간 프레임 전송 | Ethernet, Wi-Fi, ARP |
| 1. 물리 계층 | 네트워크 접근 계층 | 비트 신호를 매체로 전달 | 케이블, 전파, 광섬유 |

> 교재에 따라 TCP/IP를 **5계층**으로 나누기도 합니다. 이때는 네트워크 접근 계층을 데이터 링크 계층과 물리 계층으로 분리합니다. 4계층과 5계층 중 하나만 맞는 것이 아니라 설명 관점의 차이입니다.

### 계층화의 장점

- 역할과 책임이 분리되어 설계와 변경이 쉽습니다.
- 장애 지점을 계층별로 좁힐 수 있습니다.
  - 케이블과 무선 연결 문제: 물리·데이터 링크 계층
  - IP와 라우팅 문제: 네트워크 계층
  - 포트와 연결 문제: 전송 계층
  - 잘못된 HTTP 응답: 응용 계층
- 상위 계층은 하위 계층의 세부 구현을 몰라도 서비스를 이용할 수 있습니다.

## 2. 캡슐화와 역캡슐화

### 면접 답변

> 송신 측에서 상위 계층의 데이터에 각 계층이 필요한 헤더를 붙여 하위 계층으로 전달하는 과정을 캡슐화라고 합니다. 수신 측에서 헤더를 역순으로 해석하고 제거하여 원래 데이터를 응용 프로그램에 전달하는 과정은 역캡슐화라고 합니다.

### 데이터가 전송되는 형태

```text
응용 계층       Data
                  ↓ TCP 헤더 추가
전송 계층       Segment
                  ↓ IP 헤더 추가
인터넷 계층     Packet
                  ↓ Ethernet 헤더·트레일러 추가
링크 계층       Frame
                  ↓ 신호로 변환
물리 계층       Bits
```

수신 측은 `Bits → Frame → Packet → Segment → Data` 순서로 헤더를 해석합니다.

각 헤더에는 해당 계층이 처리할 정보가 담깁니다.

- TCP 헤더: 출발지·목적지 포트, 순서 번호, 확인 응답 번호, 플래그
- IP 헤더: 출발지·목적지 IP 주소, TTL
- Ethernet 헤더: 출발지·목적지 MAC 주소

### 알아둘 점

IP 주소는 일반적으로 출발지부터 최종 목적지까지의 논리적 주소입니다. 반면 프레임의 MAC 주소는 같은 링크에서 다음 장비로 이동할 때 사용되므로 라우터를 지날 때마다 바뀔 수 있습니다.

## 3. TCP와 UDP

### 면접 답변

> TCP는 연결 지향적이며 신뢰성 있는 바이트 스트림을 제공하는 전송 계층 프로토콜입니다. 순서 보장, 재전송, 흐름 제어, 혼잡 제어를 제공하는 대신 연결 설정과 상태 관리에 비용이 듭니다.
>
> UDP는 연결 설정 없이 데이터그램 단위로 전송합니다. 전달, 순서, 중복 방지를 보장하지 않는 대신 헤더가 단순하고 애플리케이션이 필요한 제어 방식을 직접 설계할 수 있습니다.

### 비교

| 구분 | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 | 비연결형 |
| 데이터 형태 | 경계가 없는 바이트 스트림 | 메시지 경계가 유지되는 데이터그램 |
| 신뢰성 | 순서, 재전송, 중복 제거 제공 | 전달과 순서를 보장하지 않음 |
| 제어 | 오류·흐름·혼잡 제어 | 기본적으로 제공하지 않음 |
| 헤더 크기 | 최소 20바이트 | 8바이트 |
| 브로드캐스트·멀티캐스트 | 지원하지 않음 | 가능 |
| 주요 사용 사례 | HTTP/1.1·HTTP/2, SSH, 파일 전송 | DNS, 실시간 음성·영상, 게임, QUIC의 기반 |

### TCP가 신뢰성을 제공하는 방법

- **순서 번호(Sequence Number)**: 바이트의 순서를 식별합니다.
- **확인 응답(ACK)**: 수신자가 어디까지 받았는지 알립니다.
- **재전송(Retransmission)**: 타임아웃이나 중복 ACK 등을 이용해 손실 데이터를 다시 보냅니다.
- **체크섬(Checksum)**: 전송 중 데이터 훼손을 검사합니다.
- **흐름 제어(Flow Control)**: 수신자의 처리 능력을 넘지 않도록 수신 윈도우를 이용합니다.
- **혼잡 제어(Congestion Control)**: 네트워크 상태에 맞추어 송신량을 조절합니다.

### 흐름 제어와 혼잡 제어의 차이

| 구분 | 보호 대상 | 핵심 질문 |
|---|---|---|
| 흐름 제어 | 수신자 | “수신 애플리케이션과 버퍼가 감당할 수 있는가?” |
| 혼잡 제어 | 네트워크 | “중간 네트워크가 현재 전송량을 감당할 수 있는가?” |

### 주의할 표현

- UDP가 **항상 TCP보다 빠른 것**은 아닙니다. 연결 수립과 신뢰성 제어가 적어 지연을 줄일 여지가 크다는 의미에 가깝습니다.
- 영상은 한 프레임을 잃어도 괜찮아서 무조건 UDP를 사용하는 것이 아닙니다. 실시간성과 복구 전략에 따라 UDP, TCP, QUIC 등을 선택합니다.
- QUIC은 UDP 위에서 동작하지만 신뢰성, 혼잡 제어, 암호화 같은 기능을 자체적으로 제공합니다.

## 4. TCP 연결 수립과 종료

### 3-way handshake

> TCP 통신을 시작하기 전에 클라이언트와 서버가 `SYN → SYN-ACK → ACK`를 교환하여 서로 통신 가능한지 확인하고 초기 순서 번호를 동기화하는 과정입니다.

![TCP 3-way handshake](./static/images/study/tcp-handshake.svg)

1. **클라이언트 → 서버: SYN**
   - 연결을 요청하고 클라이언트의 초기 순서 번호 `x`를 보냅니다.
2. **서버 → 클라이언트: SYN + ACK**
   - 요청을 수락하고 서버의 초기 순서 번호 `y`와 `ack=x+1`을 보냅니다.
3. **클라이언트 → 서버: ACK**
   - `ack=y+1`을 보내면 양쪽이 `ESTABLISHED` 상태가 됩니다.

### 왜 2번이 아니라 3번인가?

양쪽 모두 상대의 송신 능력과 자신의 수신 능력이 정상이며, 서로의 초기 순서 번호를 확인했다는 사실을 알아야 합니다. 마지막 ACK가 없다면 서버는 클라이언트가 서버의 SYN을 정상적으로 받았는지 확신할 수 없습니다.

### 4-way handshake

> TCP 연결은 전이중 통신이므로 각 방향을 독립적으로 닫습니다. 일반적으로 한쪽이 `FIN`을 보내면 상대가 `ACK`하고, 상대도 전송을 마친 뒤 `FIN`을 보내면 처음 종료를 요청한 쪽이 `ACK`하면서 연결을 종료합니다.

```text
Client                                      Server
  │                                            │
  │  1. FIN ─────────────────────────────────▶ │  한 방향의 전송 종료
  │  ◀───────────────────────────────── 2. ACK │
  │                                            │  남은 데이터 처리 가능
  │  ◀───────────────────────────────── 3. FIN │
  │  4. ACK ─────────────────────────────────▶ │
  │                                            │
  └── TIME_WAIT                                └── CLOSED
```

서버가 남은 데이터를 모두 처리한 상태라면 `ACK`와 `FIN`을 하나의 세그먼트로 보낼 수도 있으므로 패킷이 항상 정확히 네 개라고 단정해서는 안 됩니다.

### TIME_WAIT이 필요한 이유

- 마지막 ACK가 손실되었을 때 상대가 FIN을 재전송하면 다시 ACK할 수 있습니다.
- 이전 연결의 지연 패킷이 같은 IP와 포트 조합의 새 연결에 섞이는 것을 방지합니다.

## 5. HTTP와 HTTPS

### 면접 답변

> HTTP는 웹에서 클라이언트와 서버가 리소스를 주고받기 위한 응용 계층 프로토콜입니다. 클라이언트가 요청을 보내면 서버가 응답하는 구조이며, 각 요청은 기본적으로 독립적으로 처리되는 stateless 특성을 가집니다.
>
> HTTPS는 HTTP 메시지를 TLS로 암호화하여 기밀성, 무결성, 서버 인증을 제공하는 방식입니다.

### HTTP 메시지 구조

```http
GET /articles?page=2 HTTP/1.1
Host: example.com
Accept: application/json

```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{"items":["network-note"]}
```

- 요청: `요청 라인(method, target, version) + headers + body`
- 응답: `상태 라인(version, status code, reason) + headers + body`

### Stateless란?

서버가 프로토콜 차원에서 이전 요청의 애플리케이션 상태를 자동으로 기억하지 않는다는 의미입니다. 로그인이 필요한 서비스는 쿠키, 세션, 토큰 등을 이용해 여러 요청 사이의 사용자 상태를 연결합니다.

### “HTTP는 요청 후 항상 연결을 끊는다”는 표현이 부정확한 이유

- HTTP/1.0은 기본적으로 요청마다 연결을 닫았지만 `Keep-Alive`를 사용할 수 있었습니다.
- HTTP/1.1은 지속 연결을 기본으로 사용하여 한 TCP 연결을 여러 요청에 재사용합니다.
- HTTP/2는 하나의 연결에서 여러 요청과 응답을 동시에 처리하는 멀티플렉싱을 지원합니다.
- HTTP/3는 TCP가 아니라 QUIC을 사용합니다.

따라서 HTTP의 **stateless**와 전송 계층 연결의 유지 여부는 별개의 개념입니다.

### HTTPS가 제공하는 것

| 특성 | 의미 |
|---|---|
| 기밀성 | 중간에서 패킷을 보더라도 평문 내용을 알기 어렵게 암호화 |
| 무결성 | 메시지가 전송 중 변경되었는지 검증 |
| 인증 | 인증서를 통해 접속한 서버의 신원을 확인 |

HTTPS를 사용해도 URL의 경로와 쿼리 문자열은 브라우저 방문 기록, 서버 접근 로그, 분석 도구 등에 남을 수 있습니다. 민감한 정보를 URL에 넣지 않는 것이 좋습니다.

## 6. Cookie, Session, JWT

HTTP가 Stateless라고 해서 애플리케이션이 사용자 상태를 유지할 수 없는 것은 아닙니다. Cookie, Session, Token을 이용하면 여러 요청을 하나의 로그인 문맥으로 연결할 수 있습니다.

![Cookie, Session, JWT 인증 흐름 비교](./static/images/study/auth-state-flow.svg)

### Cookie

> Cookie는 서버가 `Set-Cookie` 응답 헤더로 브라우저에 저장하도록 지시하고, 브라우저가 조건에 맞는 후속 요청의 `Cookie` 헤더에 자동으로 포함하는 작은 Key-Value 데이터입니다.

```http
Set-Cookie: __Host-session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

| 속성 | 역할 |
|---|---|
| `Secure` | HTTPS 요청에서만 Cookie를 전송 |
| `HttpOnly` | JavaScript의 `document.cookie` 접근 차단 |
| `SameSite` | Cross-Site 요청에서 Cookie 전송 범위를 제한 |
| `Domain` | Cookie를 전송할 Domain 범위 |
| `Path` | Cookie를 전송할 URL Path 범위 |
| `Max-Age`, `Expires` | Cookie 만료 시점 |

- `HttpOnly`는 JavaScript를 통한 탈취 위험을 줄이지만 Cookie의 자동 전송은 막지 않으므로 CSRF 대응은 별도로 필요합니다.
- `SameSite=Lax` 또는 `Strict`는 CSRF 위험을 줄이는 방어 수단입니다.
- `SameSite=None`을 사용하려면 `Secure`도 함께 지정해야 합니다.
- 인증 Cookie에는 가능한 한 좁은 Domain과 Path를 사용하고 HTTPS를 적용합니다.

### Session 기반 인증

> 서버가 로그인 상태를 Session 저장소에 보관하고, 브라우저에는 그 Session을 찾기 위한 무작위 식별자만 Cookie로 전달하는 방식입니다.

```text
Browser Cookie: session_id = r4nd0m
                         │
                         ▼
Server Session Store: r4nd0m → user_id=42, role=user, expires_at=...
```

1. 사용자가 ID와 Password를 서버에 전송합니다.
2. 서버가 자격 증명을 확인하고 예측하기 어려운 Session ID를 생성합니다.
3. 서버는 Session 상태를 저장하고 Session ID를 `HttpOnly` Cookie로 전달합니다.
4. 브라우저가 후속 요청에 Cookie를 자동으로 포함합니다.
5. 서버는 Session ID로 저장소를 조회해 사용자를 식별합니다.

장점:

- 서버가 Session을 삭제하면 즉시 로그아웃·강제 만료할 수 있습니다.
- 브라우저에는 사용자 권한과 개인정보 대신 무작위 ID만 둘 수 있습니다.

고려 사항:

- 여러 서버에서 운영하면 Redis 같은 공용 Session Store나 적절한 Session Routing이 필요합니다.
- Session ID 탈취에 대비해 로그인 직후 ID를 재발급하고 만료 시간을 둡니다.
- Cookie를 사용하면 CSRF 방어가 필요합니다.

### JWT

> JWT는 Claim을 담은 JSON 객체를 URL-safe 형식으로 표현한 Token 규격입니다. 일반적인 Signed JWT는 `Header.Payload.Signature` 세 부분으로 구성되며, 서명으로 위변조 여부를 검증합니다.

```text
eyJhbGciOi...  .  eyJzdWIiOi...  .  SflKxwRJS...
└── Header ──┘    └─ Payload ─┘    └─ Signature ─┘
```

| Claim | 의미 |
|---|---|
| `iss` | Token 발급자 |
| `sub` | Token의 주체 |
| `aud` | Token 사용 대상 |
| `exp` | 만료 시각 |
| `iat` | 발급 시각 |
| `jti` | Token 고유 식별자 |

- **서명된 JWT는 암호화된 것이 아닙니다.** Payload는 Base64URL Decode로 읽을 수 있으므로 민감 정보를 넣지 않습니다.
- 서버는 허용할 서명 Algorithm을 명시하고 Token의 `alg` 값을 그대로 신뢰하지 않아야 합니다.
- Signature뿐 아니라 `iss`, `aud`, `exp` 등 필요한 Claim도 검증해야 합니다.
- Access Token은 짧게 만료시키고, 장기 로그인에는 Rotation과 폐기 정책을 갖춘 Refresh Token을 별도로 사용할 수 있습니다.
- JWT도 저장 위치에 따라 XSS 또는 CSRF의 영향을 받습니다.

### Session과 JWT 비교

| 기준 | Session ID 방식 | Self-contained JWT 방식 |
|---|---|---|
| 상태 위치 | 상태는 서버 저장소, Client에는 식별자 | 필요한 Claim을 Token에 포함 |
| 요청 검증 | Session Store 조회 | 서명과 Claim을 로컬 검증 가능 |
| 즉시 폐기 | 서버 Session 삭제로 쉬움 | 별도 Denylist·Token Version 등이 필요 |
| Token 크기 | 일반적으로 작음 | Claim과 서명 때문에 큼 |
| 확장 고려 | 공용 저장소 필요 가능 | 검증 Key 배포와 갱신 전략 필요 |
| 적합한 사례 | 일반적인 Web Login, 즉시 제어가 중요 | 서비스 간 위임, 분산된 검증이 유리 |

둘은 완전한 반대 개념이 아닙니다. JWT의 `jti`나 Refresh Token 상태를 서버에 저장할 수 있고, Session ID를 Cookie가 아닌 다른 Header로 전달할 수도 있습니다. 요구사항에 따라 조합합니다.

### 인증과 인가

- **인증(Authentication)**: 사용자가 누구인지 확인
- **인가(Authorization)**: 확인된 사용자가 특정 작업을 할 권한이 있는지 판단

Session이나 JWT는 사용자 문맥을 전달하는 수단일 뿐입니다. 서버는 각 요청에서 권한을 별도로 확인해야 합니다.

## 7. HTTP 메서드

### GET과 POST

| 구분 | GET | POST |
|---|---|---|
| 주요 목적 | 리소스 조회 | 서버에 데이터 처리를 요청하거나 하위 리소스 생성 |
| 데이터 전달 | 주로 URL의 쿼리 문자열 | 주로 요청 본문 |
| 안전성(Safe) | 서버 상태를 바꾸지 않아야 함 | 보장하지 않음 |
| 멱등성(Idempotent) | 멱등이어야 함 | 일반적으로 멱등이 아님 |
| 캐시 | 캐시하기 적합 | 명시적인 조건에서 가능하지만 일반적이지 않음 |
| 북마크·공유 | URL로 가능 | 본문은 URL에 포함되지 않음 |

> GET보다 POST가 본질적으로 더 안전한 것은 아닙니다. HTTP라면 둘 다 평문으로 노출될 수 있으며 HTTPS를 사용해야 전송 내용을 암호화할 수 있습니다. 다만 GET의 쿼리 문자열은 방문 기록과 로그 등에 더 쉽게 남습니다.

### PUT과 PATCH

| 구분 | PUT | PATCH |
|---|---|---|
| 의미 | 요청 대상 리소스의 전체 상태를 생성하거나 대체 | 리소스의 일부 변경 사항을 적용 |
| 일반적인 멱등성 | 멱등 | 문서 형식과 연산에 따라 다름 |
| 예시 | 사용자 설정 전체 교체 | 사용자 닉네임만 변경 |

```http
PUT /users/42
Content-Type: application/json

{"name":"Reo","email":"reo@example.com"}
```

```http
PATCH /users/42
Content-Type: application/json

{"name":"New Reo"}
```

### 자주 사용하는 메서드

| 메서드 | 용도 |
|---|---|
| GET | 리소스 조회 |
| POST | 데이터 처리, 하위 리소스 생성 |
| PUT | 리소스 전체 생성·대체 |
| PATCH | 리소스 일부 수정 |
| DELETE | 리소스 삭제 |
| HEAD | 응답 본문 없이 GET과 같은 헤더 조회 |
| OPTIONS | 서버가 지원하는 통신 옵션 확인 |

## 8. HTTP 상태 코드

HTTP 상태 코드는 요청 처리 결과를 세 자리 숫자로 표현합니다. 첫 번째 숫자가 응답의 큰 범주를 나타냅니다.

| 범위 | 의미 | 대표 코드 |
|---|---|---|
| 1xx | 처리 중인 정보 응답 | `100 Continue` |
| 2xx | 요청 성공 | `200 OK`, `201 Created`, `204 No Content` |
| 3xx | 추가 동작·리다이렉션 필요 | `301 Moved Permanently`, `302 Found`, `304 Not Modified` |
| 4xx | 클라이언트 요청 문제 | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` |
| 5xx | 서버 처리 실패 | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` |

### 자주 혼동하는 코드

- `401 Unauthorized`: 이름과 달리 주로 **인증되지 않음**을 의미합니다.
- `403 Forbidden`: 신원은 알더라도 해당 리소스에 접근할 권한이 없음을 의미합니다.
- `502 Bad Gateway`: 게이트웨이·프록시가 상위 서버로부터 유효하지 않은 응답을 받았습니다.
- `503 Service Unavailable`: 과부하나 점검 등으로 서버가 일시적으로 요청을 처리할 수 없습니다.

## 9. 브라우저에 URL을 입력하면 일어나는 일

### 면접 답변

> 브라우저가 URL을 해석한 뒤 캐시와 DNS를 통해 서버 IP를 찾습니다. 다음 홉의 MAC 주소를 확인하고 라우터를 거쳐 서버와 연결합니다. HTTPS라면 TCP 연결과 TLS 협상을 수행한 후 HTTP 요청을 보냅니다. 서버는 애플리케이션 로직을 처리해 응답하고, 브라우저는 HTML을 파싱하면서 CSS와 JavaScript 같은 추가 리소스를 요청한 뒤 화면을 렌더링합니다.

![브라우저 URL 요청 흐름](./static/images/study/browser-request-flow.svg)

### 단계별 흐름

#### 1. URL 해석

브라우저가 다음 요소를 분리합니다.

```text
https://www.example.com:443/articles?id=10#summary
└─scheme  └────host────┘ port └─path─┘ query  fragment
```

`fragment`는 브라우저 내부에서 사용되며 HTTP 요청으로 서버에 전달되지 않습니다.

#### 2. 캐시와 DNS 조회

1. 브라우저와 운영체제의 DNS 캐시를 확인합니다.
2. 캐시에 없다면 설정된 재귀 DNS 리졸버에 질의합니다.
3. 리졸버는 필요하면 Root → TLD → Authoritative DNS 서버를 따라가며 레코드를 찾습니다.
4. 도메인의 `A` 또는 `AAAA` 레코드를 통해 IPv4 또는 IPv6 주소를 얻습니다.

CDN을 사용하면 DNS 결과가 사용자의 위치와 네트워크 상태에 가까운 엣지 서버를 가리킬 수 있습니다.

#### 3. 로컬 네트워크에서 다음 홉 확인

목적지가 같은 네트워크인지 서브넷 마스크로 판단합니다. 외부 네트워크라면 기본 게이트웨이로 프레임을 보내야 하므로 ARP(IPv4) 또는 Neighbor Discovery(IPv6)를 이용해 다음 홉의 링크 계층 주소를 확인합니다.

#### 4. 서버까지 패킷 전달

IP 패킷은 여러 라우터를 거칩니다. 각 라우터는 라우팅 테이블을 보고 다음 경로를 선택합니다. 이 과정에서 링크 계층 프레임은 홉마다 새로 만들어지지만 최종 목적지 IP는 일반적으로 유지됩니다. NAT 환경에서는 공인·사설 IP와 포트가 변환될 수 있습니다.

#### 5. 연결과 보안 협상

- HTTP/1.1·HTTP/2: 일반적으로 TCP 3-way handshake 후 TLS handshake를 수행합니다.
- HTTP/3: UDP 기반 QUIC이 연결과 TLS 1.3 보안 협상을 통합해 수행합니다.
- TLS 과정에서 서버 인증서를 검증하고 이후 통신에 사용할 암호화 키를 합의합니다.

#### 6. HTTP 요청과 서버 처리

브라우저가 요청을 보내면 웹 서버·리버스 프록시·애플리케이션 서버 등이 요청을 처리합니다. 필요한 경우 캐시, 데이터베이스, 외부 API를 조회한 뒤 HTTP 응답을 만듭니다.

#### 7. 브라우저 렌더링

1. HTML을 파싱하여 DOM을 만듭니다.
2. CSS를 파싱하여 CSSOM을 만듭니다.
3. JavaScript를 내려받아 실행합니다.
4. DOM과 CSSOM으로 렌더 트리를 구성합니다.
5. Layout → Paint → Composite 과정을 거쳐 화면을 표시합니다.

HTML 파싱 도중 발견한 CSS, JavaScript, 이미지, 폰트는 별도의 HTTP 요청으로 가져올 수 있습니다.

### 관점별로 요약하기

| 관점 | 주요 관심사 |
|---|---|
| 네트워크 | DNS, ARP·ND, 라우팅, TCP·QUIC, TLS, 패킷 전달 |
| 백엔드 | 프록시, 라우팅, 인증, 비즈니스 로직, 캐시, DB, 응답 생성 |
| 프론트엔드 | HTML 파싱, 리소스 로딩, JavaScript 실행, 렌더링 |

## 10. 핵심 용어

| 용어 | 설명 |
|---|---|
| 프로토콜 | 통신 주체가 메시지를 주고받기 위해 합의한 형식과 규칙 |
| PDU | 계층별 데이터 단위. 전송 계층의 세그먼트·데이터그램, 네트워크 계층의 패킷, 링크 계층의 프레임 등 |
| 포트 | 한 호스트 안에서 통신 대상 프로세스를 구분하는 번호 |
| 소켓 | 일반적으로 IP 주소, 포트, 전송 프로토콜 등을 이용하는 통신 종단점 |
| RTT | 패킷을 보내고 응답이 돌아오기까지 걸리는 왕복 시간 |
| 대역폭 | 단위 시간에 전송할 수 있는 데이터의 양 |
| 지연 시간 | 데이터가 출발지에서 목적지까지 도달하는 데 걸리는 시간 |
| DNS | 도메인 이름을 IP 주소 등의 레코드로 변환하는 분산 시스템 |
| ARP | IPv4 네트워크에서 같은 링크의 IP 주소에 대응하는 MAC 주소를 찾는 프로토콜 |
| 라우팅 | 목적지 IP까지 패킷을 전달할 다음 경로를 선택하는 과정 |
| NAT | 사설 주소와 공인 주소·포트를 변환하는 기술 |
| TLS | 통신의 암호화, 무결성, 상대 인증을 제공하는 보안 프로토콜 |
| 쿠키 | 브라우저가 저장하고 조건에 따라 HTTP 요청에 포함하는 작은 데이터 |
| 세션 | 여러 요청을 하나의 사용자 문맥으로 연결하기 위해 서버 등이 관리하는 상태 |
| JWT | JSON Claim을 URL-safe 형식으로 표현하고 서명 또는 암호화할 수 있도록 정의한 Token 규격 |
| Access Token | 보호된 Resource에 접근할 권한을 나타내는 수명이 짧은 Token |
| Refresh Token | 새로운 Access Token을 발급받기 위해 사용하는 상대적으로 수명이 긴 Credential |
| CSRF | 사용자가 로그인한 상태를 악용해 원하지 않는 요청을 보내게 하는 공격 |
| XSS | 공격자의 Script가 신뢰받는 Page 문맥에서 실행되는 취약점 |
| 멱등성 | 같은 요청을 여러 번 수행해도 한 번 수행한 것과 서버의 의도된 최종 상태가 같은 성질 |
| 안전한 메서드 | 서버의 상태를 변경하지 않는 읽기 목적의 HTTP 메서드 |
